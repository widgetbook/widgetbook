# For Designers

Widgetbook Cloud has two audiences: the developers who build the UI and the designers who own how it should look. Most of these docs are written for developers. This section is written for you — the designer — and assumes you have never opened a Flutter project and never will.

You do not need to run any code, check out a branch, or install anything. Every pull request produces a [review](/cloud/reviews) you open in your browser, where you compare the implementation against your design and leave feedback the developer sees directly on the change.

  New to the words developers use around this workflow? Start with the
  [Glossary](/cloud/for-designers/glossary). It is a short translation table, and

## The two-stage review

A single UI review has two passes, and they are usually done by two different people.

1. **Filter out the unintended.** The developer who opened the pull request reviews it first, looking for changes they did *not* mean to make — a component that shifted because a shared value changed, spacing that moved, a state that now renders differently. They resolve those before asking anyone else to look.
2. **Judge whether it is right.** Once only intentional changes remain, the next reviewer decides whether those changes are *correct*. When that is a design question — does this match the intended design, is this the right treatment for this state — that reviewer is you.

The first pass is a filter. **A review that reaches you should contain only deliberate changes.** Your job is not to hunt for accidents the developer already caught; it is to judge whether the deliberate changes are right.

# Glossary for Designers

Developer vocabulary that shows up in a pull request, a review, or a Slack message.

| Term | What it means |
| --- | --- |
| [**Pull request**](/cloud/visual-pull-request/overview) (PR) | A proposed set of changes to the app, waiting to be reviewed and merged. Every reviewer submits their own review on it. GitLab calls it a *merge request*. |
| [**Story**](/stories/overview) | One component in one specific state, for example a button when disabled. It stays interactive in Widgetbook, so args and addon values can be changed while looking at it. |
| [**Scenario**](/testing/overview) | A story frozen into a fixed state so it can be captured automatically. One story can have several scenarios. |
| [**Snapshot**](/cloud/snapshots/overview) | The screenshot of one scenario. One scenario produces one snapshot per build. |
| [**Build**](/cloud/builds/overview) | One version of the code, hosted as a browsable Widgetbook and captured as snapshots. A review compares two builds. |
| **Base / Head** | The two sides of the comparison. **Base** is the existing version, already merged. **Head** is the proposed version. The review labels these **Baseline** (left) and **Latest** (right). |
| [**Approve / Request changes**](/cloud/reviews/submit) | The decision on a review. Approve marks the pull request as accepted, request changes marks it as rejected until revised, and comment records feedback without either. |
| **Merge** | Accepting a pull request so its changes become part of the app. |
| **Commit status** | The check Widgetbook Cloud reports back to GitHub, GitLab, Azure DevOps, or Bitbucket. A requested change turns it red and blocks the merge. |

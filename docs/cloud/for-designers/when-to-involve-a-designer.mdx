# Decide When to Review

Not every pull request needs a design review.
A designer pulled into a change with no open design questions is wasted time.
A designer skipped on a change that has open questions lets a deviation ship.
Two things decide the policy: how confident the developer is in the change, and how well the team's design intent has held up before.

Widgetbook Cloud supports this through [required reviewers](/cloud/reviews/required-reviewer).
A project can require design approval, or leave the developer to [request a designer](/cloud/reviews/request-reviewer) per pull request.
Which of the three policies below a team uses is a team decision, not a product setting.

## On demand (recommended default)

The developer invites a designer only when the change warrants it:

- The developer struggled with something.
- The developer had to guess at a state the design did not specify.
- The developer has an open question to answer before merging.

The developer requests the designer as a reviewer.
The designer is notified and reviews that pull request.

Involving a designer early is cheap.
At review time the work is real enough to judge, but nothing is built on top of it yet.
A correction here changes one pull request.
The same correction after the component ships and gets reused changes many.

## Trust-based

The developer is confident, and designers have historically trusted that judgement.
Reviews of this developer's work rarely surface design problems.
No design review is needed.
The developer merges after code and UI review, and designer attention stays on the changes that need it.

## Always

Designers have historically found deviations in this team's work.
Every pull request requires design approval before it can merge.
Enforce this with [required reviewers](/cloud/reviews/required-reviewer): a designated designer must approve before a pull request counts as approved.

<Warning>
  Treat "always" as a temporary correction, not a permanent state.
  Requiring design approval on every pull request stops the bleeding while the team fixes why deviations keep happening.
  Permanent enforcement is not the goal.
  As the cause is addressed, move back toward on-demand review.
</Warning>

## A deviation is not automatically the developer's fault

Do not skip this.
This framing matters more than the policy the team picks.

When a review turns up a change that does not match the design, the reflex is to blame the developer.
Often the cause is different.
An ambiguous or incomplete design forces a best guess.
A reasonable guess that turns out wrong is a specification problem, not a coding one.

A deviation that keeps showing up, the same kind of finding across many reviews, points at a gap in the design, not a pattern of carelessness.
Common sources:

- **An undesigned state.** Empty, loading, error, and edge states the design never specified, so the developer invented one.
- **A missing design system component.** The design uses something that does not exist yet in the shared system, so it gets approximated.
- **Unspecified responsive behaviour.** What the layout should do at narrow or very wide sizes was never defined.
- **Unspecified accessibility behaviour.** Focus order, semantics, or contrast expectations were never written down.
- **Raw values instead of tokens.** The design specifies a literal colour or spacing value rather than a token, so implementations drift.

Fix the source, not the symptom.
Design the missing state.
Add the component to the design system.
Specify the behaviour.
A review gate catches the deviation every time, but a fixed specification leaves nothing to catch.

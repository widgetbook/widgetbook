# Accessibility Regression Testing

Accessibility regression testing compares the **accessibility tree** of your UI between two versions and flags what changed. The accessibility tree is the structured data that screen readers and other assistive technologies read, so a change to it is a change to how your app works for the people who depend on them.

## Why It Matters

Accessibility bugs are invisible. Drop a button's label, change its role, or reorder the tree, and the screen looks exactly the same. Code review misses it because the widget diff looks harmless. Visual review misses it because no pixel moved. The only way to catch it is to read the accessibility tree, which nobody does by hand on every pull request.

That is the gap this closes. Widgetbook Cloud diffs the accessibility tree of every [scenario](/testing/overview) between the `base` and `head` [builds](/cloud/builds/overview) of a pull request and shows the changes in your existing [review](/cloud/reviews). Regressions become visible before merge, with no extra tooling and no manual screen-reader passes.

It catches the changes visual testing cannot:

- A `Semantics` label dropped from a button, so screen-reader users hear nothing.
- A role changing from a button to plain text, or a heading losing its level.
- Nodes reordered, so assistive technologies read the screen in the wrong order.
- Nodes silently added to or removed from the tree.

## Visual vs. Accessibility Regression

Both run on the same builds and in the same review:

|                | Visual regression                                                          | Accessibility regression                                                             |
| -------------- | -------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| **Comparison** | **Screenshots** between `base` and `head` [builds](/cloud/builds/overview) | **Accessibility trees** between `base` and `head` [builds](/cloud/builds/overview)    |
| **Catches**    | Layout shifts, color changes, overflow, clipping                           | Missing labels, changed roles, reordered nodes, dropped or added accessibility nodes  |

## How It Works

1. During testing, `testWidgetbook` captures the accessibility tree of every scenario alongside its screenshot and evaluates a set of [accessibility guidelines](/cloud/accessibility/guidelines).
1. The [Widgetbook CLI](/cloud/builds/upload) uploads this data with the build's [snapshots](/cloud/snapshots/overview). No extra step.
1. When a pull request has builds for both the `base` and `head` commits, Widgetbook Cloud diffs the two accessibility trees per scenario.
1. Differences appear as **Accessibility Changes** on the story diff, ready to be [reviewed](/cloud/accessibility/review) alongside visual changes.

## Requirements

<Info>
Accessibility regression testing requires **Widgetbook 4** and the **Widgetbook CLI 4** (`{{ versions.cli }}`). Only Widgetbook 4 builds capture and upload accessibility data. Widgetbook 3 builds are compared visually only.
</Info>
